# 技術スタックの選定

技術スタックが未決の場合に読む。**既に確立済みの環境がある場合(過去プロジェクトの流用、チームの標準、指定がある)は、このファイルを読む必要はない。既存の環境を使うのが常に最善**で、慣れた環境の生産性は技術の優劣を簡単に上回る。

## 判断軸(この順で効く)

1. **AIコーディングとの相性** — 最重要。学習データが多い枯れた技術ほどAIは正確に書ける。新しい・ニッチ・急速に破壊的変更が入るものは、AIが古い書き方を出して詰まる。**流行っているかではなく、情報が蓄積しているかで選ぶ**
2. **非エンジニアが結果を確認できるか** — ディレクターがブラウザで開く、実行ファイルをダブルクリックするなど、コードを読まずに動作確認できる経路があるか。ビルドや環境構築が複雑な選択肢は、それだけで検証サイクルが止まる
3. **配信先の要件を満たすか** — 目的のプラットフォームに出せるか。Steam配信、スマホストア配信、ブラウザ配信で選択肢が変わる
4. **必要な表現力** — 2Dか3Dか、必要なパフォーマンス、物理演算やアニメーションの要求水準
5. **将来の移植可能性** — プロトタイプが本開発に進む場合、ロジックだけ持ち出せる構造にできるか(claude-md-template.mdの「systems/はエンジン非依存」の原則と接続)

## 選定の進め方

1. 企画から前提を確定する: **配信先 / 2Dか3Dか / オンライン要素の有無 / プロトタイプか本開発か / 開発体制(一人かチームか)**
2. 前提が絞れたら、**候補を2つに絞って推奨と理由を提示する**。3つ以上並べると非エンジニアは選べない。「A案/B案、推奨はA、理由は〜、Aを選ばない場合のデメリットは〜」の形
3. **選ばなかった側のトレードオフを必ず書く**。後から「なぜこれにしたんだっけ」を辿れるようにするため。決定内容はspec.mdかCLAUDE.mdに「なぜこの構成か」として1〜2行残す
4. **最新の状況を検索で確認してから提示する**。エンジンやフレームワークの推奨構成、ライセンス条件、対応プラットフォームは変わる。記憶だけで断定しない(特にライセンス・料金体系は企業の方針変更が起きる領域)

## 典型的な分岐

以下は出発点であり、確定的な推奨ではない。**該当しそうな選択肢が出たら、現在の状況・ライセンス・対応環境を検索で確認する**。

- **ブラウザで動かしたい / プロトタイプで素早く検証したい** → Web技術(TypeScript + ビルドツール)。2Dゲームならゲーム用ライブラリを併用。**リンクを送るだけで誰でも触れる**ため、非エンジニアの検証サイクルが最も速い。プロトタイプ段階の第一候補になりやすい
- **Steamで配信したい / 3Dが必要 / 本格的な開発** → ゲームエンジン。この場合、エンジンごとにライセンス条件・料金体系・得意分野が異なるため、必ず現行条件を確認する
- **スマホアプリとして出したい** → ストア配信の要件(審査、ネイティブ機能、課金SDK)を満たせる構成か。Web技術のラップで足りるか、ネイティブ/エンジンが要るかは、要求する体験の水準で決まる
- **ツール・自動化・データ処理** → ゲームエンジンは不要。スクリプト言語で足りることが多い

## よくある失敗

- **プロトタイプに本開発の技術を選ぶ** — 検証したいのは「面白いか」であって「作れるか」ではない。プロトタイプは最速で触れる形を優先し、本開発で作り直す前提でよい。ロジックをエンジン非依存に書いておけば、作り直しのコストは大幅に下がる
- **やりたいことに対して過剰な選択** — 2Dの小規模ゲームに重量級の3Dエンジンを選ぶと、学習・ビルド・確認のすべてが遅くなる
- **AIが不得意な技術を選ぶ** — 非エンジニアがAIに書かせる前提では、これは致命傷になる。「AIが書けない技術は、自分では直せない」ことを意味する
- **途中で乗り換える** — 一度決めたら固定する。CLAUDE.mdの「技術スタック(固定・変更禁止)」はこのための宣言。乗り換えたくなったら、それは選定時の前提確認が足りなかったサインなので、次の企画に活かす

## 決定後

決定した構成を claude-md-template.md の `{{ }}` に流し込む。あわせて、その構成でロジックと表示を分離する具体的な形(どのディレクトリがエンジン非依存か)を決めて、CLAUDE.mdに明記する。
