### 文書の置き場

リポジトリ直下に置いてよい文書は **AGENTS.md / CLAUDE.md / WORKLOG.md / README.md** だけ。
それ以外の .md と .txt は、作る前に下の表で置き場を決める。直下に新しい文書を作ることは禁止。

| 作りたいもの | 置き場 | ファイル名 |
|---|---|---|
| 仕様の本体 | docs/spec.md | 固定。1本だけ |
| 追加仕様、変更提案、設計メモ | docs/specs/ | `SPEC-YYYYMMDD-内容.md` |
| 作業ログの切り出し | docs/worklog/ | `WORKLOG_YYYY-MM-DD.md` |
| 調査メモ、検討メモ、手順書 | docs/notes/ | `NOTE-YYYYMMDD-内容.md` |
| 詰まった症状と回避策 | docs/KNOWN_ISSUES.md | 固定。追記のみ |
| 外部AI向けの現状要約 | docs/PROJECT_SUMMARY.md | 固定。上書き |

- 置き場に迷ったら docs/notes/ に入れる。直下には置かない
- 検査は `node scripts/check-docs.mjs`(npm のないプロジェクトは `sh scripts/check-docs.sh`)。`npm run check` に含め、pre-commit でも実行する。検査に落ちた状態で完了報告をしない
- 直下に許可外の文書を見つけたら `sh scripts/migrate-docs.sh` で移し、WORKLOG.md の「経緯」に1行書く。参照しているリンクも直す
- docs/specs/ の追加仕様は、採用が決まったら docs/spec.md に統合し、元ファイルは残す。未採用のものは先頭に「状態: 保留」か「状態: 不採用」を書く

### 最重要ルール: systems/ はエンジン非依存

- systems/ 内は「入力(状態+経過時間)→出力(新状態)」の純関数で書く
- 理由: (a) テストで数式を直接検証できる (b) 本番エンジンへの移植時にロジックだけ持ち出せる (c) 表示とロジックの混線によるバグを構造で防ぐ
- 画面側はsystemsを呼んで結果を描画するだけの「薄い皮」にする
- systems/ の関数は**受け取った引数を書き換えない**。新しい状態を作って返す。名前と戻り値から分からない変更(ついでの保存、別の値の加算、グローバルな値の更新)を中でしない
- 保存・通信・時刻・乱数のように外とやりとりするものは systems/ の外に置き、必要な値は引数で渡す。こうすると関数の中を読まなくても、引数と戻り値だけで何が起きるかが決まる

### データ駆動の徹底

- 名前、数値、テキスト、確率などゲームの中身は**すべて src/data/ に置く**。コードに直書きしない(マジックナンバー禁止)
- バランス調整は data/balance.ts の数値変更だけで完結する状態を保つ

## 6. 各タスクの完了条件(Definition of Done)

タスク完了を報告する前に、必ず以下を自分で実行して通すこと。

1. `npm run check`(型チェック + 文書の置き場の検査)がエラー0
2. `npm run test` が全パス
3. `npm run dev` を起動し、該当機能をブラウザで操作して動作確認した旨と確認手順を報告
4. spec.mdの該当フェーズの受け入れ条件を1項目ずつ照合し、結果を○×で報告

受け入れ条件を満たせない項目がある場合、勝手に仕様を変えて満たしたことにしない。「未達+理由」を報告する。

### 6.1 状態の定義(「実装済み」と「完了」を混同しない)

フェーズや項目の状態は次のいずれかで報告する。コードが存在するだけでは「完了」ではない。

| 状態 | 意味 |
|---|---|
| 未着手 | 実装を始めていない |
| 実装中 | コードを変更している |
| ローカル検証済み | check/test/ブラウザ確認を通した |
| 実環境検証待ち | 本番相当の環境(実機・配信先・本番データ)での確認が残っている |
| 完了 | 受け入れ条件と必要な検証をすべて満たした |
| 保留 | ディレクターの判断や外部要因を待っている |

ローカルでしか確認できていないものを「完了」と書かない。「実装済み・実環境検証待ち」とする。

「受け入れ条件を満たした」と「本流(mainブランチ)に入った」は別の事実。受け入れ条件の充足を報告しても、マージが済むまでフェーズは完了ではない。マージの入力はコミットのみとし、作業ツリーからファイルを直接コピーして取り込まない(中間状態や、コード以外の成果物の取りこぼしが差分に見えないまま起きる)。

### 6.2 完了報告の形式(証拠中心)

「実装しました。問題なく動作しています」は報告ではない。次の形式で、第三者が追跡できる情報を書く。

```
## 結果
- 対象: {{フェーズ/仕様ID}}
- 受け入れ条件の照合: (1項目ずつ○×)

## 検証
- 型チェック: エラー0
- テスト: N件成功 / M件失敗
- ブラウザ確認: (確認した操作手順)
- 未実施の検証: (あれば必ず書く。なければ「なし」)

## Git
- 開始時HEAD / 終了時HEAD
- 変更ファイル一覧

## 残事項
- 未達項目とその理由
- 新しく見つけて別タスクにした問題(§7.1参照)
```

すべて成功したように見せることより、未確認を未確認のまま正確に書くことを優先する。

### 6.3 完了を口にする前の検証ゲート

「完了」「直った」「通る」「問題ない」と書く前に、必ずこの順で通す。1つでも飛ばしたら、それは検証ではなく推測。

1. その主張を証明するコマンドは何かを特定する
2. そのコマンドを**今**、省略なしで実行する(前回の結果は使えない)
3. 出力を最後まで読み、終了コードと失敗件数を確認する
4. 出力が主張を裏付けているか判断する。裏付けなければ、実際の状態を証拠つきで書く
5. ここまで通って初めて主張を書く

| 主張 | 必要な証拠 | 証拠にならないもの |
|---|---|---|
| テストが通る | 今回のテスト出力で失敗0件 | 前回の結果、「通るはず」 |
| ビルドが通る | ビルドコマンドの終了コード0 | 型チェックが通った、ログが綺麗 |
| バグが直った | 元の現象を再現する操作で再現しない | コードを変えた、直ったと思う |
| 受け入れ条件を満たした | spec.mdの条件を1項目ずつ○×で照合 | テストが通った |
| サブエージェントが完了した | git diff で変更を確認 | サブエージェントの「成功」報告 |

「〜のはず」「おそらく」「〜と思われる」を成果の説明に使わない。使いたくなったら、まだ検証が済んでいない。

### 6.4 二段階レビュー(サブエージェントに任せる場合)

フェーズや仕様IDの単位で別のエージェントに実装を任せた場合、実装者の報告を鵜呑みにせず、**別の新しいエージェント**にレビューさせる。実装者自身に自分の成果をレビューさせない。

レビューは必ず**仕様適合 → コード品質**の順で、分けて見る。同時に見ると片方が甘くなる。

**第1段: 仕様適合**
実装者の報告は「検証されていない主張」として扱う。diffと spec.md の該当IDを突き合わせ、次の3種を探す。
- 欠落: 求められていたのに実装されていない、または「実装した」と書いてあるが diff にない
- 過剰: 求められていない機能、先回りの作り込み
- 誤解: 正しい機能を間違った形で作った、違う問題を解いた

diff だけでは判定できない項目は「diff からは確認不能」として報告し、範囲を広げて探し回らない。

**第2段: コード品質**
第1段が通ってから見る。責務の分離、エラー処理、テストが実際の挙動を検証しているか(モックを検証していないか)、§2 のディレクトリ規則に従っているか。

**重大度の付け方**
- Critical: 直すまでこの成果を信用できない(受け入れ条件の未達、誤った挙動)
- Important: マージを止める水準の問題(握りつぶされたエラー、何も検証していないテスト、ロジックの丸ごと重複)
- Minor: 磨き込み(「テストをもっと増やせる」はここ)

全部をCriticalにしない。逆に、実装者の「YAGNIなので省いた」「意図的にシンプルにした」という言い訳で重大度を下げない。

**レビュー報告の形式**
```
## 仕様適合
- 受け入れ条件: (1項目ずつ○×、diffから確認不能なら△と理由)
- 欠落 / 過剰 / 誤解: (あれば file:line つきで)

## 良い点
(具体的に。実装者が残りの指摘を信頼できるように)

## 指摘
### Critical / ### Important / ### Minor
(各項目: file:line、何が問題か、なぜ問題か、直し方が自明でなければ直し方)

## 判定: 承認 / 要修正
```

**修正ラウンドの上限**
要修正なら実装者に戻す。修正のたびに、変更範囲に絞った再レビューを行う。**修正は最大5ラウンド**。3ラウンドで収束しなければ、4ラウンド目は新しい実装者を立てる(同じ実装者は同じ間違いを繰り返す)。5ラウンドで収束しなければ止まり、残った指摘を §9.1 の形式で報告する。これは E-2(同じバグの修正試行)と同じ考え方で、回数を重ねるほど場当たり修正が増える。

**進捗の記録場所**
進捗は会話の記憶ではなく WORKLOG.md に書く(§11)。会話が圧縮されると記憶は消えるが、ファイルと git log は残る。再開時は自分の記憶より WORKLOG.md の「現在地」と git log を信じる。完了済みのフェーズを再実装しない。

### 6.5 テストの信頼度を数値で確かめる

{{TypeScript/JavaScript など、ミューテーションテストの道具が標準的に使えるスタックの場合のみ残す。Godot(GDScript)・Roblox・アセンブラ等では削除し、代わりに §6.4 のレビューで「テストが実際の挙動を検証しているか」を重点的に見させる}}

テストが全部通っていても、そのテストが何も守っていないことがある。期待値を実装に合わせて書き換えた、アサーションの中身が空、テストを消して通した、などの場合である。コードを読まずにこれを見抜くために、**ミューテーションテスト**を使う。コードにわざと小さな誤りを埋め込み、テストがそれを検出できた割合(Kill率)を測る手法で、検出されずに生き残った誤りは「その箇所をテストが守っていない」ことを示す。

- 対象は `src/systems/`(純粋ロジック)に限る。画面側には当てない
- 実行はフェーズ完了時のみ。時間がかかるので、タスクごとには回さない
- 道具: {{例: Stryker。導入は §1 の事前承認制に従う}}
- 初回の Kill率を基準値として WORKLOG.md の「現在地」に記録する。以後のフェーズで基準値を下回ったら、完了報告の「残事項」に書く
- 生き残った誤りのうち、spec.md の数式・判定(ダメージ計算、確率、報酬、解放条件など)に関わるものは、テストを追加してから完了とする。表示用の整形やログ出力に関わるものは、理由を書いて見送ってよい
- Kill率を上げるためにテストの期待値を実装から逆算して書かない。期待値の根拠は spec.md に置く

完了報告(§6.2)の「検証」欄に、フェーズ完了時は次の1行を足す。

```
- ミューテーションテスト: Kill率 N%(基準値 M%) / 生き残りのうち仕様に関わるもの K件 → 対応内容
```

### 6.6 変更が別の場所を壊さないかを確かめる(影響範囲の確認)

{{リリース済み・テスト配信中など、本番データや外部の利用者がいるプロジェクトでは必ず残す。出す前のプロトタイプだけなら削除してよい}}

テストが通っても、差分の外にあるものは守られていない。保存データ、サーバーとクライアントがやりとりする中身、マスタ、管理画面、別のアプリが同じデータを読む箇所などである。次の変更では、完了報告の前にこの確認を行う。

- セーブデータ、サーバーの保存先(DBの列)、通信の中身(送受信するJSON)の形を変える変更
- 課金、報酬、ランキング、マスタの読み込みに触る変更
- 小さいが、ディレクターが「念のため確かめて」と言った変更

**確認の進め方**

1. **変更の中身を書き出す。**追加・変更・削除したもの、そして差分に書かれていない挙動の変化(呼ばれる順番、保存されるタイミング、初期値)
2. **「これが成り立てば安全」と言える事実を1つか2つ決める。**例:「この変更で書き換わるのは新規作成のデータだけで、既存のセーブは読み方も中身も変わらない」。怖そうなケースを長く並べるより、この1つに時間を使う
3. **名前の検索では見つからない場所を見る。**保存済みのデータ、通信の中身、DBの列、マスタ、管理画面、別の言語で同じデータを読むコード、機能の切り替えフラグ、使っているライブラリの版。呼び出し元を並べるだけで終えない(検索すれば数秒で分かるので、それは確認ではない)
4. **その事実を、実際のコードを動かして確かめる。**確からしさは次の5段階で書き、どこまで到達したかを明記する

| 段階 | 中身 |
|---|---|
| 1 | 言っただけ。これだけでは根拠にならない |
| 2 | 該当するファイルと行を示した |
| 3 | 悪いケースが起きないことを、処理を一歩ずつたどって示した |
| 4 | **実際のコードを呼ぶ小さなスクリプトかテストを書いて実行した**(間違っていれば失敗する形で) |
| 5 | 動いているアプリで再現して確かめた |

**段階4に届かなかった事実は「未証明」と書く。**安全だと言い切らない。段階4は通常、本体と同じライブラリを読み込み、問題の関数を直接呼ぶ数十行のスクリプトで足りる。

完了報告(§6.2)の「検証」欄の下に、次の節を足す。

```
## 影響範囲
- 変更の中身: (差分に書かれていない挙動の変化も含む)
- 安全の根拠: (事実を1つ) → 段階N / 証明済み・未証明
- 証明: (実行したスクリプトと結果)
- 残るリスク: (壊れ方 / ファイル:行 / 起きやすさと起きたときの重さ / 確かめ方)
- 確認して問題なしとしたもの: (何を見て、なぜ問題ないか)
- マージ前に足すとよいテスト: (いちばん安く本物の不具合を捕まえるもの)
```

存在しない呼び出し元やAPIを書かない。探して見つからなかったことは「見つからなかった(どう探したか)」と書く。起きやすさと重さを大きく見せない。

### 6.7 約束の表からテストを先に作る

spec.md の計算・判定に付いた「約束の3点」(入力の条件・結果の約束・いつでも守ること)は、テストの元になる。実装は次の順で進める。

1. spec.md の表を読み、テストを先に書く。最低限、次の3種類を入れる
   - 入力の条件の**境界**(ちょうど下限、ちょうど上限、下限の1つ下、上限の1つ上)
   - 結果の約束の**代表値**(表の例にある値と、端数処理が効く値)
   - いつでも守ることの**確認**(呼ぶ前後で、入力に渡した状態が変わっていない、範囲から外れていない)
2. テストが落ちることを確かめる
3. テストが通るように実装する

表に無い条件を思いついたら、実装で勝手に決めずに §7 に従って質問する。
完了報告(§6.2)の「検証」欄には、spec.md の ID ごとに「境界 N件／代表値 N件／守ること N件」を書く。

## 7. 仕様との向き合い方

- spec.mdに書いていないことを実装しない。書いてあることを省略しない
- 仕様が曖昧・矛盾している場合は、実装で勝手に解決せず**質問する**。質問は「A案/B案、推奨はA、理由は〜」の形式で
- 仕様のIDを参照してコミュニケーションする

### 7.1 作業中に見つけた別の問題の扱い

作業中に別のバグや改善点を見つけたら、現在のタスクに混ぜる前に次の三択で判定する。

1. 現在の受け入れ条件を満たすために必須 → 現在のタスク内で扱う
2. 関連はあるが、現在の受け入れ条件とは別 → 完了報告の「残事項」に記載し、現在の作業を続ける
3. 無関係な既存問題 → 同上

2と3を勝手に現在のタスクへ含めない。1件のタスクが際限なく膨らむのを防ぐため。

## 8. Git運用

- コミットは機能単位で小さく。メッセージは日本語1行
- 指示「push」のみで add→commit→push を実行してよい
- mainブランチ直コミットでよい(プロトタイプのため)。初期ブランチ名はmainにする

## 9. エスカレーション基準(上位モデルに渡す領域)

### うまく進まないときの原因の切り分け

行き詰まったら、上位モデルに渡す前に、原因が次のどれかを先に判定する。対処が違うので、混ぜて報告しない。

| 原因 | 見分け方 | 対処 |
|---|---|---|
| 情報が足りない | spec.md に書かれていない、仕様同士が矛盾している、守るべきテストがない、既存コードの意図が読み取れない | 上位モデルに渡さない。§7 に従って質問するか、足すべき仕様・テストを具体的に提案して止まる |
| 権限・環境が足りない | コマンドが実行できない、必要なファイルや外部サービスに届かない、ライブラリの追加が要る | 上位モデルに渡さない。何ができなかったか、何があれば進むかを §9.1 の形式で報告する |
| 能力が足りない | 情報も権限も揃っているのに解けない。下の E-番号に該当する | 上位モデル案件として止まる |

「情報が足りない」を「能力が足りない」として報告しない。モデルを替えても、書かれていない仕様は分からない。

### 上位モデルに渡す基準

以下に該当する作業は、着手せずに「上位モデル案件」とだけ報告して止まること。

- E-1: アーキテクチャの変更提案(ディレクトリ構成、状態管理方式、シーン構成の変更)
- E-2: 同じバグへの修正を**2回試みて直らなかった**場合。3回目を試みない。現象・試したこと・仮説を整理して止まる
- E-3: パフォーマンス問題の原因調査
- E-4: セーブデータのマイグレーションが本当に必要になった場合
- E-5: バランス数式の再設計(数値変更はよいが、式の構造変更は上位モデル)
- E-6: spec.mdの矛盾が3箇所以上見つかった場合

### 9.0 不具合を直す前の調べ方

E-2 は「2回直らなかったら止まる」と定めているが、その2回を場当たりに使わないための手順。**原因を特定する前に修正案を出さない。** 症状だけを直すのは失敗として扱う。

**手順1: 原因の特定**
- エラーメッセージとスタックトレースを最後まで読む(答えが書いてあることが多い)
- 確実に再現できる手順を作る。再現しないなら情報が足りていない。推測で直さない
- 直前の変更を見る(git diff、直近のコミット、設定変更)
- 複数の層(入力 → systems/ → 表示、クライアント → サーバー)にまたがる場合、各層の境界で入出力をログに出して**どの層で壊れているか**を先に絞る
- 悪い値がどこで生まれたかを呼び出し元へさかのぼる。症状の場所ではなく発生源で直す

**手順2: 動いている例との比較**
- 同じコードベースで似た機能が動いていれば、それとの差分を全部列挙する。「これは関係ないだろう」で除外しない

**手順3: 仮説を1つ立てて最小の変更で試す**
- 「Xが原因だと思う。理由はY」と一文で書く
- 一度に1つだけ変える。複数を同時に変えると、どれが効いたか分からなくなる
- 効かなければ、上に重ねず元に戻して別の仮説を立てる
- 分からないときは「Xが分からない」と書いて §9.1 で止まる。分かったふりをしない

**手順4: 修正**
- 修正の前に、その不具合を再現する最小のテストを書く(再現テストがない修正は再発する)
- 修正は1つだけ。「ついでに」の改善やリファクタリングを混ぜない
- §6.3 のゲートを通してから「直った」と書く

**次の言葉が頭に浮かんだら、手順1に戻る**
「とりあえず直して後で調べる」「Xを変えてみて様子を見る」「たぶんXなので直す」「テストは省いて手で確認する」「よく分からないがこれで動くかもしれない」

**2回失敗したら E-2 で止まる。** 修正のたびに別の場所で新しい問題が出る、修正に大きな作り直しが要る、という状態は「仮説が外れた」のではなく「構造が間違っている」。E-1 として報告する。

### 9.1 止まるときの報告形式

エスカレーション基準に該当して止まるとき、および仕様の質問で止まるときは、次の3節で報告する。ディレクターがそのまま判断できる形にする。

```
## 停止理由
(該当するE-番号 or 仕様ID と、何が起きたか)

## 確認済み
- 参照した箇所: (spec.mdのID、ファイル名)
- 現在の実装の挙動
- ファイル変更: あり/なし(ありなら一覧)
- Git状態: 開始時からの差分の有無

## 判断が必要な点
(A案/B案、推奨はA、理由は〜)
```

止まったことは失敗ではない。根拠なく進めて手戻りを増やすより安全な成果として扱う。

### 9.2 別解を並べて選ぶ(アリーナ)

設計の分かれ道(E-1)や、原因が絞れない不具合(E-2 で止まった後)では、1回の試行で形が決まってしまうのを避けるため、**同じ課題を複数の実装者に別々に解かせ、良いものを選ぶ**手がある。使用量が数倍かかるので、**自分の判断で始めない。**§9.1 で止まる報告の「判断が必要な点」に、アリーナを使う案として書き、ディレクターの承認を得てから行う。

**進め方**

1. **課題を1つの文にする。**全員が同じ文を受け取るので、ここが契約になる。作るもの、守る仕様のID、触ってよい範囲を書く
2. **採点の基準を3〜6個、先に決める。**(例: spec.md の受け入れ条件を満たすか / 既存のセーブを壊さないか / 変更行数 / 次の機能を足しやすいか)。基準は選ぶ側だけが使い、実装者には見せない
3. **実装者を2〜3体、別々の作業場所で同時に走らせる。**作業場所は git worktree(同じリポジトリの別コピー)を使い、互いの結果を見せない。可能なら別のモデル(Claude Code と Codex など)にする。各実装者には成果物と、検討して捨てた案とその理由を短く書かせる
4. **採点は、実装者とは別のモデルに読み取り専用で任せる。**全員が書き終わってから始める
5. **選ぶ側も全部を最後まで読む。**基準ごとに点を付け、採点役の推薦と比べる。食い違ったら、両方の理由を読んでから決める。迷ったら、次に手を入れる人が壊しにくい方(境界がはっきりしている、公開する関数が少ない)を選ぶ
6. **選ばなかった案から、良い部分を1〜2点だけ移す。**貼り付けずに、選んだ案の考え方に合わせて書き直す
7. **結果の読み方:** 全員が同じ形に落ち着いたら、それが答えとして強い。全員がばらばらなら、平均を取らず、課題の文(手順1)を書き直してやり直す
8. **選んだ成果物も §6.3 の検証ゲートを通す。**検証で問題が出たら、課題の文が悪かったのか、移し忘れなのかを見て戻る

WORKLOG.md に、選んだ案、移した部分(どの案から)、捨てたもの、脱落した実装者、検証結果を短く残す。

## 10. 禁止事項まとめ

- 無断のライブラリ追加 / 仕様外機能の実装 / 勝手なリファクタリング
- systems/ へのエンジン依存の持ち込み / 現在時刻の直接使用
- ロジック・データのコード直書き / anyの使用
- 完了条件チェックを省いた完了報告 / 2回失敗したバグの3回目の修正試行
- 検証コマンドを今回実行せずに「通る」「直った」と書くこと / 原因を特定する前に修正案を出すこと
- 実装者自身に自分の成果をレビューさせること / サブエージェントの「成功」報告をdiff確認なしに信じること
- テストを通すために期待値を実装から逆算すること / テストを削除・無効化して通したことにすること / 情報不足を能力不足として報告すること
- 影響範囲の確認(§6.6)で、実行して確かめていないことを「安全」と書くこと / 承認なしにアリーナ(§9.2)を始めること
- systems/ の関数で引数を書き換えること / 範囲の外れた値を黙って丸めること / 約束の表(§6.7)にない条件を実装で勝手に決めること

### WORKLOG.md の運用

2部構成にする。

```
## 現在地
| フェーズ | 状態(§6.1) | 終了時HEAD | 未解決の指摘 |
(フェーズごとに1行。上書きして常に最新にする)

## 経緯
### YYYY-MM-DD
(その日の作業の流れを追記。判断した内容と理由、詰まった点、次にやること)
```

- 「現在地」は**上書き**、「経緯」は**追記**
- 経緯が長くなったら(目安: 200行、または1週間)、古い分を `docs/worklog/WORKLOG_YYYY-MM-DD.md` に切り出す。WORKLOG.md には「現在地」と直近の経緯だけを残す
- 切り出したファイルはリポジトリ直下に置かない。docs/worklog/ 以外の場所に作らない
- 同じ日に複数回切り出す場合は `WORKLOG_YYYY-MM-DD-a.md` `-b.md` と枝番を付ける

### KNOWN_ISSUES.md の運用

§9.0 の手順で調べて分かったこと、E-番号で止まって解決したことは、ここに残す。1件の形式は「症状 / 原因 / 回避策または恒久対応 / 関連する仕様ID・コミット」。同じ症状に当たったら、まずここを見る。

### PROJECT_SUMMARY.md の運用

「このプロジェクトは何か / 今どのフェーズか / 主要な設計判断 / 既知の制約」を、会話履歴を持たない外部のAIが読んで作業に入れる粒度で書く。フェーズが完了するたびに更新する。長さは A4 で2枚を超えない。

### changelog の運用

テスターに見せる更新履歴は、**変更のたびに1件ずつ足す**。後からまとめて書かない。まとめ書きは漏れが出るし、テスターに届かないまま実機に入ることがある。
