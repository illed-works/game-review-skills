## 2. ディレクトリ構成(固定)

```
src/
  data/        ゲームデータ定義のみ。ロジック禁止
  systems/     純粋ロジックのみ。{{エンジン名}}のimport禁止
  scenes/      画面({{エンジン名}}側)
  ui/          再利用UI部品
  types/       型定義
```

### 最重要ルール: systems/ はエンジン非依存

- systems/ 内は「入力(状態+経過時間)→出力(新状態)」の純関数で書く
- 理由: (a) テストで数式を直接検証できる (b) 本番エンジンへの移植時にロジックだけ持ち出せる (c) 表示とロジックの混線によるバグを構造で防ぐ
- 画面側はsystemsを呼んで結果を描画するだけの「薄い皮」にする

### データ駆動の徹底

- 名前、数値、テキスト、確率などゲームの中身は**すべて src/data/ に置く**。コードに直書きしない(マジックナンバー禁止)
- バランス調整は data/balance.ts の数値変更だけで完結する状態を保つ

## 3. コーディング規則

- TypeScript strict。`any` 禁止。`as` キャストは原則禁止(必要なら理由をコメント)

- 凝った抽象化・デザインパターン・先回りの汎用化は**禁止**。spec.mdにある機能をそのまま素直に書く

## 4. 時間の扱い

## 6. 各タスクの完了条件(Definition of Done)

タスク完了を報告する前に、必ず以下を自分で実行して通すこと。

1. `npm run check`(型チェック)がエラー0
2. `npm run test` が全パス
3. `npm run dev` を起動し、該当機能をブラウザで操作して動作確認した旨と確認手順を報告
4. spec.mdの該当フェーズの受け入れ条件を1項目ずつ照合し、結果を○×で報告

受け入れ条件を満たせない項目がある場合、勝手に仕様を変えて満たしたことにしない。「未達+理由」を報告する。

### 6.1 状態の定義(「実装済み」と「完了」を混同しない)

フェーズや項目の状態は次のいずれかで報告する。コードが存在するだけでは「完了」ではない。

| 状態 | 意味 |
|---|---|
| 未着手 | 実装を始めていない |
| 実装中 | コードを変更している |
| ローカル検証済み | check/test/ブラウザ確認を通した |
| 実環境検証待ち | 本番相当の環境(実機・配信先・本番データ)での確認が残っている |
| 完了 | 受け入れ条件と必要な検証をすべて満たした |
| 保留 | ディレクターの判断や外部要因を待っている |

ローカルでしか確認できていないものを「完了」と書かない。「実装済み・実環境検証待ち」とする。

「受け入れ条件を満たした」と「本流(mainブランチ)に入った」は別の事実。受け入れ条件の充足を報告しても、マージが済むまでフェーズは完了ではない。マージの入力はコミットのみとし、作業ツリーからファイルを直接コピーして取り込まない(中間状態や、コード以外の成果物の取りこぼしが差分に見えないまま起きる)。

### 6.2 完了報告の形式(証拠中心)

「実装しました。問題なく動作しています」は報告ではない。次の形式で、第三者が追跡できる情報を書く。

```
## 結果
- 対象: {{フェーズ/仕様ID}}
- 受け入れ条件の照合: (1項目ずつ○×)

## 検証
- 型チェック: エラー0
- テスト: N件成功 / M件失敗
- ブラウザ確認: (確認した操作手順)
- 未実施の検証: (あれば必ず書く。なければ「なし」)

## Git
- 開始時HEAD / 終了時HEAD
- 変更ファイル一覧

## 残事項
- 未達項目とその理由
- 新しく見つけて別タスクにした問題(§7.1参照)
```

すべて成功したように見せることより、未確認を未確認のまま正確に書くことを優先する。

## 7. 仕様との向き合い方

- spec.mdに書いていないことを実装しない。書いてあることを省略しない
- 仕様が曖昧・矛盾している場合は、実装で勝手に解決せず**質問する**。質問は「A案/B案、推奨はA、理由は〜」の形式で
- 仕様のIDを参照してコミュニケーションする

### 7.1 作業中に見つけた別の問題の扱い

作業中に別のバグや改善点を見つけたら、現在のタスクに混ぜる前に次の三択で判定する。

1. 現在の受け入れ条件を満たすために必須 → 現在のタスク内で扱う
2. 関連はあるが、現在の受け入れ条件とは別 → 完了報告の「残事項」に記載し、現在の作業を続ける
3. 無関係な既存問題 → 同上

2と3を勝手に現在のタスクへ含めない。1件のタスクが際限なく膨らむのを防ぐため。

## 9. エスカレーション基準(上位モデルに渡す領域)

以下に該当する作業は、着手せずに「上位モデル案件」とだけ報告して止まること。

- E-1: アーキテクチャの変更提案(ディレクトリ構成、状態管理方式、シーン構成の変更)
- E-2: 同じバグへの修正を**2回試みて直らなかった**場合。3回目を試みない。現象・試したこと・仮説を整理して止まる
- E-3: パフォーマンス問題の原因調査
- E-4: セーブデータのマイグレーションが本当に必要になった場合
- E-5: バランス数式の再設計(数値変更はよいが、式の構造変更は上位モデル)
- E-6: spec.mdの矛盾が3箇所以上見つかった場合

### 9.1 止まるときの報告形式

エスカレーション基準に該当して止まるとき、および仕様の質問で止まるときは、次の3節で報告する。ディレクターがそのまま判断できる形にする。

```
## 停止理由
(該当するE-番号 or 仕様ID と、何が起きたか)

## 確認済み
- 参照した箇所: (spec.mdのID、ファイル名)
- 現在の実装の挙動
- ファイル変更: あり/なし(ありなら一覧)
- Git状態: 開始時からの差分の有無

## 判断が必要な点
(A案/B案、推奨はA、理由は〜)
```

止まったことは失敗ではない。根拠なく進めて手戻りを増やすより安全な成果として扱う。

## 10. 禁止事項まとめ

- 無断のライブラリ追加 / 仕様外機能の実装 / 勝手なリファクタリング
- systems/ へのエンジン依存の持ち込み / 現在時刻の直接使用
- ロジック・データのコード直書き / anyの使用
- 完了条件チェックを省いた完了報告 / 2回失敗したバグの3回目の修正試行
