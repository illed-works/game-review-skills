構成(ID制、スコープ外、データ全件確定、数式、フェーズ+受け入れ条件、実装しない判断リスト)は崩さない。`{{ }}` を埋め、章はプロジェクトに応じて増減してよいが、削ってよいのはゲーム内容の章のみ。§1(目的とスコープ外)、フェーズ計画、最終章(実装しない判断)は必須。

書き方の鉄則:
- 全仕様にID(S-1, S-2...)を振る
- 数値・確率・費用・時間は具体値で確定。「適切に」「バランスよく」禁止
- データはユーザーへの質問ではなく、こちらでたたき台の表を作って提示→修正してもらう
- 受け入れ条件は「非エンジニアがブラウザで触って目視確認できる文」で書く
- 計算・判定には**約束の3点**(入力の条件・結果の約束・いつでも守ること)を表で付ける。AIはこの表からテストを先に作り、ディレクターはコードではなくこの表で検収する

## 7. フェーズ計画と受け入れ条件

各フェーズはこの順で実装する。フェーズ完了ごとに受け入れ条件を○×報告(AGENTS.md §6)。

**受け入れ条件の書き方**

- 「何をすれば満たしたと分かるか」が一意に読める文にする。判定の解釈でAIが迷う余地を残さない
- 曖昧: 「エラーが出ないこと」→ 何を数えるか不明。警告を含むかで判断が割れる
- 明確: 「コンソールに `Error` を含む行が0件」「タイトルからゲーム開始まで操作が3回以内」
- 数値・文字列・回数で言えるものは必ずそう書く。目視確認の条件も「〜が画面に表示される」「タップで〜に遷移する」まで具体化する

**体感目標(§7.1)は受け入れ条件とは別に書く**。数値にできない狙いを受け入れ条件に混ぜると判定不能になる。

### 7.2 検証コマンド

各フェーズの受け入れ条件のうち、コマンドで判定できるものはコマンドを書く。

- {{P1}}: `{{npm run test -- phase1}}`
- {{P2}}: `{{実際に打つコマンド}}`

**書いたコマンドは、実装を始める前に一度そのまま実行して確認する**(通る必要はない。未実装なら落ちて正常)。見ているのは「そのコマンドが存在するか」「返ってくるか」の2点。存在しないコマンドや返ってこないコマンドを仕様に書いたまま渡すと、実装側がそこで詰まる。
