# game-dev-kit: 非エンジニア向けAI開発キット生成

## このスキルの目的

企画書はあるがコードは書けないディレクターが、AIコーディング(Claude Code)に開発を任せて、**コードを読まずに検収できる**状態を作る。成果物は2ファイル:

1. **CLAUDE.md** — AIへの恒久指示(書き方のルール、ガードレール、エスカレーション基準)
2. **spec.md** — 仕様の唯一の正(何を作るかの完全定義、フェーズ計画、受け入れ条件)

この2ファイルの品質が、廉価モデル(Sonnet)で開発が安定して回るかを決める。

## 設計思想(この5原則を必ず守る)

### 原則1: 判断の余地を仕様側で潰す

AIコーディングの事故の大半は「難しいコード」ではなく「仕様に書いてない部分をAIが自分で決めた場面」で起きる。だからspec.mdでは:

- 全仕様にIDを振る(S-1, S-2...)。実装・質問・報告はID参照で行わせる
- 数値(確率、費用、時間、量)はすべて具体値で確定させる。「適切に」「バランスよく」は禁止
- データ(キャラ、アイテム、ステージ等)は表形式で全件確定させる
- **「実装しないと決めたもの(質問不要)」の章を必ず設ける**。スコープ外の明記は、スコープの定義と同じくらい重要
- 曖昧・矛盾があれば実装せず質問せよ、というルールをCLAUDE.md側に置く

### 原則2: 構造でバグを防ぐ

- **ロジックと表示の分離を強制する**(例: systems/はゲームエンジンimport禁止の純関数のみ)。表示とロジックの混線がAIコーディング最大の事故源
- 数式・判定ロジックには**ユニットテストを義務化**(ケース数を仕様に明記)
- 時間を扱うゲームでは、現在時刻の直接取得を禁止し、倍速切替できるClock経由に統一(放置・クールダウン等の検証を数秒で行うため)
- ゲームデータはコードに直書きせずdata/ディレクトリに分離(バランス調整をデータ変更だけで完結させる)

### 原則3: コードを読まない検収を成立させる

- 開発を**フェーズ分割**し、各フェーズに**受け入れ条件のチェックリスト**を付ける
- AIには「完了報告の前に自分で検証を通す」ことを義務付ける: 型チェック→テスト→ブラウザ/実機で操作確認→受け入れ条件を○×で照合報告
- 受け入れ条件は「ディレクターがブラウザで触って目視確認できる文」で書く(「〜が表示される」「タップで〜できる」)。内部実装の条件にしない
- 受け入れ条件は**判定の解釈が割れない文言**まで落とす。「エラーが出ない」ではなく「コンソールに `Error` を含む行が0件」。数値・回数・文字列で言えるものは必ずそう書く
- 数値にできない狙い(**体感目標**)は受け入れ条件に混ぜず、spec.mdの別節に1行ずつ置く。受け入れ条件は「実装されたこと」しか検証できないので、「狙いが満たされたこと」の判断基準を別に渡す
- コマンドで判定できる受け入れ条件は**検証コマンド**を仕様に書く。書いたコマンドは実装開始前に一度そのまま実行し、「存在するか」「返ってくるか」だけ確かめる(通る必要はない)
- **accept と merge は別の事実**として扱わせる。受け入れ条件の充足報告とマージ完了を混同させない
- 「完了」「直った」と書く前に**検証ゲート**を通させる。証明するコマンドを特定→今実行→出力を読む→主張、の順。前回の結果や「〜のはず」は証拠にしない
- サブエージェントに実装を任せる場合は、**別の新しいエージェントに仕様適合→コード品質の順で二段階レビュー**させる。実装者の報告は「未検証の主張」として扱わせ、修正は最大5ラウンドで上限を切る
- テストが通っていても、そのテストが何も守っていないことがある。対応する道具があるスタックでは、フェーズ完了時に**ミューテーションテスト**(コードにわざと誤りを埋め、テストが検出できた割合を測る)を純粋ロジックに当てさせ、Kill率を報告させる。コードを読まずにテストの手抜きを数字で見抜く手段になる。道具のないスタックではこの節を削る
- 本番データや外部の利用者がいるプロジェクト(リリース済み・テスト配信中)では、保存データ・通信の中身・課金・マスタに触る変更のたびに**影響範囲の確認**をさせる。「これが成り立てば安全」という事実を1つ決め、実際のコードを動かすスクリプトかテストで確かめさせる。確からしさを5段階で書かせ、実行して確かめていないものは「未証明」と書かせる。出す前のプロトタイプだけなら §6.6 を削る
- 進捗は会話ではなく **WORKLOG.md** に書かせる。冒頭「現在地」(上書き)＋その下「経緯」(追記)の2部構成。長くなった分は `docs/worklog/` に切り出させ、リポジトリ直下を汚さない
- WORKLOG のほかに **KNOWN_ISSUES.md**(詰まった症状と回避策)、**PROJECT_SUMMARY.md**(外部AIに渡す現状要約)を docs/ に置き、誰がいつ書くかを表で固定する。テスター配布があるなら changelog も
- 未達項目を勝手に仕様変更で「達成したこと」にするのを明示的に禁止する
- **「実装済み」と「完了」を分ける**。状態を「ローカル検証済み/実環境検証待ち/完了」で区別させ、実機や配信先で未確認のものを完了と呼ばせない
- 完了報告は作業内容ではなく**証拠**(テスト件数、未実施の検証、開始/終了のコミット)を中心にした定型で書かせる。肝は「未確認を未確認のまま書かせる」こと
- 作業中に見つけた別の問題は「今の受け入れ条件に必須か/関連するが別か/無関係か」の三択で切り分け、後二者は残事項に回して現在作業を続けさせる(スコープ膨張の防止)

### 原則4: エスカレーション基準を機械的に定義する

廉価モデルに「難しくなったら頑張る」をさせない。上位モデル(Fable/Opus)に渡す条件をCLAUDE.mdに列挙する:

- 同じバグの修正に**2回失敗したら3回目を試みず止まる**(最重要。無限修正ループが最大の時間泥棒)
- アーキテクチャ・ディレクトリ構成・状態管理方式の変更提案
- パフォーマンス問題の原因調査
- 数式の構造変更(数値変更は廉価モデルでよい)
- 仕様の矛盾が3箇所以上見つかった場合

上位モデルに渡す前に、行き詰まりの原因を**情報が足りない/権限・環境が足りない/能力が足りない**の3つに切り分けさせる。上位モデルに渡すのは3つ目だけで、前の2つは質問か報告で止まらせる。書かれていない仕様は、モデルを替えても分からない。

止まるときは「停止理由/確認済み/判断が必要な点」の3節で報告させる。ディレクターが報告を読んでそのまま決められる形にするため。

設計の分かれ道や、2回直らなかった不具合では、**アリーナ**(同じ課題を2〜3体の実装者に別々の作業場所で解かせ、別のモデルに採点させて良いものを選び、他の案から良い部分を1〜2点だけ移す)を案として出させる。使用量が数倍かかるので、AIに自分の判断で始めさせず、停止報告の「判断が必要な点」に書かせてディレクターの承認を取る。全員が同じ形に落ち着けば答えとして強く、ばらばらなら課題の書き方を直してやり直す。

E-2(2回失敗で止まる)の2回を場当たりに使わせないため、**不具合を直す前の調べ方**を手順として置く。原因の特定→動いている例との比較→仮説を1つ立てて最小変更→再現テストを書いてから修正、の順。原因を特定する前に修正案を出させない。

加えて「土台フェーズ(P0)だけ上位モデルでやる」ことを納品時にユーザーに推奨する。土台の質が以降の廉価モデルの安定度を決める。

### 原則5: 禁止事項を明文化する

CLAUDE.mdに必ず含める禁止リスト:
- 無断のライブラリ追加(承認制)
- 仕様外機能の実装 / 先回りの汎用化・凝った抽象化
- 頼まれていない箇所のリファクタリング
- any等の型逃げ / マジックナンバー直書き
- 検証を省いた完了報告

## 作業手順

### Step 1: 会話履歴から吸い上げる

企画書や仕様の相談が同じ会話・過去の会話にあるなら、まずそこから抽出する(ユーザーに再説明させない)。確認すべき項目:

- 何を検証/実現したいのか(プロトタイプなら検証目的を1文で)
- 技術スタック(過去プロジェクトで確立済みの環境があればそれを流用。例: Phaser+TypeScript+Vite)。**未決の場合は `references/stack-selection.md` を読んでから選定に入る**(既に決まっているなら読まなくてよい)
- 対象プラットフォーム(ブラウザ/スマホ縦横/PC)
- ゲームの核となるループとデータ(キャラ・部屋・アイテム等の種類と数)

### Step 2: 足りない情報だけ質問する

一度に全部聞かない。**決定が必要な論点を2〜3個に絞って質問→回答を反映→次へ**のリズムで進める。各質問には推奨案と理由を添える(「A案/B案、推奨はA、理由は〜」)。技術用語は避けるか、使う場合は一言で説明を添える。

数値やデータ表は、ユーザーに全部決めさせず**こちらで具体値のたたき台を作って提示し、直してもらう**。ゼロから聞くより10倍速い。

### Step 2.5: 技術スタックが未決なら選定する

スタックが決まっていない場合のみ、`references/stack-selection.md` を読んで選定する。前提(配信先・2D/3D・オンライン要素の有無・プロトタイプか本開発か・開発体制)を確定させ、**候補を2つに絞って推奨と理由、選ばなかった場合のトレードオフ**を提示する。3つ以上並べない。

**オンライン要素がある場合は、サーバー/インフラの実行環境もこの段階で確定させる。** クライアント側より手戻りが大きく、後から決めると書いたコードが広範囲に使えなくなる。

決定したら、その理由を1〜2行でCLAUDE.mdかspec.mdに残す。ここで決めた構成は以降固定する。

### Step 3: spec.mdを書く

`references/spec-md-template.md` を読み、その構成に従って書く。プロジェクト固有の内容で全セクションを埋める。テンプレの構成(ID制、スコープ外、データ表、数式、フェーズ+受け入れ条件、実装しない判断リスト)は崩さない。

### Step 4: CLAUDE.mdを書く

`references/claude-md-template.md` を読み、技術スタック・ディレクトリ構成・プロジェクト概要だけ差し替える。原則2〜5に関わるルール部分はテンプレのまま維持する(弱めない)。

ファイル構成は、本文をAGENTS.mdに書き、CLAUDE.mdは `@AGENTS.md` のインポート1行とClaude固有の追記だけにする(Codexと共用するため)。

spec.md は `docs/spec.md` に置く。リポジトリ直下に置く文書は AGENTS.md / CLAUDE.md / WORKLOG.md / README.md の4つだけで、それ以外は docs/ 配下にする。テンプレ §11 の文書表に従い、WORKLOG.md(「現在地」「経緯」の見出しだけ)、docs/KNOWN_ISSUES.md、docs/PROJECT_SUMMARY.md、docs/worklog/(空)、docs/specs/(空)、docs/notes/(空) の骨格も一緒に作る。テスター配布がないプロジェクトでは changelog の行を消す。

**文書の置き場を機械的に守らせる(必須)。** ルールで言うだけではAIは直下に文書を作るので、検査を仕込む:

1. `assets/docs-layout/scripts/`(check-docs.mjs、check-docs.sh、migrate-docs.sh)と `assets/docs-layout/.githooks/pre-commit` を、そのままキットの `scripts/` と `.githooks/` にコピーする。中身を書き換えない(許可リストを変える場合だけ、mjs と sh の `ALLOW` を同時に直す)
2. spec.md の P0 受け入れ条件に「`npm run check` は型チェックの後に `node scripts/check-docs.mjs` を実行する」「`git config core.hooksPath .githooks` が設定されている」を入れる。npm のないスタック(Godot 等)では `sh scripts/check-docs.sh` を手動または CI で実行する旨を書く
3. 既存リポジトリに後から入れる場合は、納品時の説明に `sh scripts/migrate-docs.sh` を1回実行する手順を足す

スタックがWeb系ライブラリ(React/Next.js/Vite/Phaser/TypeScript等)の場合は、テンプレの「ライブラリの書き方を推測しない」節を残し、context7で最新ドキュメントを確認させるルールを入れる。指示のたびに「use context7」と書くのは続かないので、恒久指示側に置くこと。Godot・Roblox・アセンブラ等の対象外スタックではこの節を削除する。

### Step 4.5: 会話の痕跡を消す(自動・必須)

ファイルを書き出す前に、必ず `sanitize-artifacts` スキルのチェックリストを2ファイルに当てる。spec.mdとCLAUDE.mdは壁打ちの積み重ねで作るため、「前回と違い」「〜は使わない方針」「ご指示のとおり」のような会話由来の記述が混ざりやすい。制約は説明文ではなく設計(書かない・単純にする)として反映する。ユーザーに「整えますか」と聞かず、黙って実施する。

### Step 5: 納品時の説明

2ファイルを渡す際、必ず以下を平易に伝える:

1. 使い方: AGENTS.md / CLAUDE.md / WORKLOG.md をリポジトリ直下、spec.md と他の文書を docs/ に置き、初回は「AGENTS.mdとdocs/spec.mdを読んでからP0を開始して」と指示する
2. モデル運用: P0は上位モデル推奨、P1以降は廉価モデル、エスカレーション基準に該当したら上位モデルに切替(/modelコマンド)
3. 検収方法: フェーズごとの○×報告と受け入れ条件を照合し、ブラウザで触って確認する。コードは読まなくてよい
4. 途中の許可確認への対応: 検証コマンド(check/test/dev)やgit操作は即Yes、npm install(ライブラリ追加)だけは「spec.mdに必要?」と聞き返す

## 品質チェックリスト(納品前に自分で確認)

- [ ] spec.mdの全仕様にIDが振られているか
- [ ] 数値・確率・費用に「適切に」等の曖昧語が残っていないか
- [ ] データ表(キャラ等)が全件確定しているか
- [ ] 「実装しないもの」「実装しない判断を既にしたもの」の章があるか
- [ ] 各フェーズの受け入れ条件が「非エンジニアが目視確認できる文」かつ判定が一意に決まる文言になっているか
- [ ] 体感目標の節があり、数値化できない狙いが1行ずつ書かれているか
- [ ] 検証コマンドを書いた場合、渡す前に一度実行して存在と応答を確認したか
- [ ] CLAUDE.mdにロジック/表示分離・テスト義務・完了条件・エスカレーション基準・禁止事項が揃っているか
- [ ] 状態定義(実装済み≠完了)・証拠中心の完了報告形式・別問題の三択切り分け・停止時の報告形式が残っているか
- [ ] 原因の切り分け表(§9冒頭)が残っているか。ミューテーションテスト(§6.5)は、道具のあるスタックでは残し、ないスタックでは削除したか
- [ ] 検証ゲート(§6.3)・二段階レビュー(§6.4)・不具合の調べ方(§9.0)が残っているか。サブエージェントを使わない小規模案件でも §6.3 と §9.0 は削らない
- [ ] 本番データや外部の利用者がいるプロジェクトなら影響範囲の確認(§6.6)が残っているか(出す前のプロトタイプだけなら削除したか)。アリーナ(§9.2)が承認制のまま残っているか
- [ ] 文書表(§11)があり、spec.md が docs/ に、WORKLOG の切り出し先が docs/worklog/ になっているか。リポジトリ直下の文書が4つ(AGENTS/CLAUDE/WORKLOG/README)に収まっているか
- [ ] scripts/check-docs.mjs・check-docs.sh・migrate-docs.sh と .githooks/pre-commit を assets からコピーし、P0 の受け入れ条件に check-docs の実行と hooksPath の設定が入っているか
- [ ] Web系スタックならcontext7参照ルールが入っているか(対象外スタックなら削除されているか)
- [ ] sanitize-artifactsのチェックリストを通し、会話の痕跡(指示への言及、避けた案の説明、修正履歴)が残っていないか
- [ ] 2ファイル間で矛盾がないか(特にディレクトリ構成とフェーズ参照)

## 出典

CLAUDE.mdテンプレートの §6.3(検証ゲート)・§6.4(二段階レビュー)・§9.0(不具合の調べ方)は、[obra/superpowers](https://github.com/obra/superpowers)(MIT)の verification-before-completion / subagent-driven-development / systematic-debugging を元に、非エンジニアが検収する前提と本キットの語彙(受け入れ条件・○×照合・E-番号)に合わせて書き直したもの。

§6.5(テストの信頼度を数値で確かめる)と §9 冒頭(原因の切り分け)は、mizchi「俺のAIプログラミング手法(2026/10/05)」の「/goal と一緒に使う評価指標」「考える順番」の考え方を元に、本キットの検収の流れに合わせて書いたもの。

§6.6(影響範囲の確認)と §9.2(アリーナ)は、[cursor/plugins](https://github.com/cursor/plugins) の pstack(poteto、MIT)にある blast-radius / arena スキルを元に、非エンジニアの検収とゲーム開発で壊れやすい場所(セーブデータ・通信・課金・マスタ)に合わせて書き直したもの。アリーナは使用量が大きいため、元のスキルと違ってディレクターの承認制にしている。
