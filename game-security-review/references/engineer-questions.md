# engineer-questions.md — エンジニアに投げる質問と、答えの読み方

このファイルの目的は、**コードが読めなくても危険を判定できるようにする**こと。質問文はそのまま貼れる形で提示し、返ってきた答えを🟢/🟡/🔴に分類できる基準を必ずセットにする。

## 使い方の原則

- **「大丈夫ですか?」と聞かない。** ほぼ確実に「大丈夫です」と返ってくるが、それは検証ではなく印象。**「どこで決めていますか」「どうやって防いでいますか」と、事実を答えさせる形で聞く**
- **一度に全部投げない。** まず下の【最優先5問】だけ投げる。ここが赤なら、他は後回しでよい
- **相手が社内の別担当・外注なら、指摘ではなく確認の形にする。** 「これ危ないですよ」で始めると防御反応が出て、事実が出てこなくなる。「リリース前の確認事項として、経営から聞かれそうな点をまとめました」等、**第三者の要求という体裁**にすると通りやすい
- **回答が抽象的なら、もう一段聞く。** 「対策済みです」「暗号化しています」は答えになっていない。**何を、どこで、どう** の3つが揃うまで聞く

---

## 【最優先5問】ここだけで大半の重大リスクが判定できる

### Q1. 課金アイテムやゲーム内通貨を付与するとき、「何をいくつ付与するか」を決めているのは、サーバーとクライアントのどちらですか?

- 🟢 サーバーが商品IDから自分でマスタを引いて決めている / クライアントは「購入した」という事実だけ送る
- 🟡 クライアントも送るが、サーバーが必ず突き合わせて不一致なら弾いている(**突き合わせ処理の実在を確認する**)
- 🔴 クライアントが送ってきた個数・アイテム・価格をそのまま使っている

### Q2. 同じ購入・報酬受け取りのリクエストが2回届いたとき、2回付与されない仕組みは何ですか?

- 🟢 リクエストごとの一意なID(冪等キー)またはトランザクションIDを記録し、処理済みは無視している
- 🟡 「受け取り済みフラグ」で防いでいる(**フラグ更新と付与が同じトランザクション内か**を追加で確認)
- 🔴 特に対策していない / 「普通は2回来ないので大丈夫」

### Q3. クライアント(ブラウザに配信されるファイル)の中に、サーバー側のAPIキーやデータベースの接続情報は含まれていませんか? 含まれている鍵があれば、それは公開前提の鍵ですか?

- 🟢 サーバー側の鍵は一切含まれない / 含まれるのは公開前提の鍵のみで、権限設定で守っている
- 🟡 公開前提の鍵が含まれるが、権限設定を確認していない(**設定の中身を見せてもらう**)
- 🔴 サーバー側の秘密鍵・DB接続情報・管理用トークンが含まれている(**発見時点で鍵の無効化と再発行が必要**)

### Q4. あるプレイヤーのAPIリクエストで、他人のIDを指定したら他人のデータが返ってきたり更新できたりしませんか? どこでそれを防いでいますか?

- 🟢 操作対象は認証トークンから決めており、リクエスト内のIDは使っていない/照合して不一致なら拒否している
- 🟡 一部のAPIだけ照合している(**全エンドポイントに漏れなく効いているかを確認**)
- 🔴 IDを指定すればアクセスできる / 確認していない

### Q5. 不正が起きたとき、通貨やアイテムがいつ・誰に・何によって増えたかを後から追えるログは残っていますか? また、ガチャや購入など特定の機能だけを止める手段はありますか?

- 🟢 増減ログがあり、機能単位でサーバー設定から止められる
- 🟡 ログはあるが保存期間が短い / 止めるにはクライアントの再ビルドが必要
- 🔴 ログがない、または止める手段がない(**穴が見つかっても、被害範囲も特定できず、止めることもできない**)

## 【追加の質問】構成に応じて投げる

### 課金がある場合

> ストアのレシート検証は、サーバーからストアの検証APIに問い合わせる形になっていますか? また、同じレシートを二度使えないようトランザクションIDを保存していますか?

🔴: クライアント側で検証している / レシートの使い回しを防いでいない

> (Web決済の場合)アイテム付与のきっかけは、ユーザーが決済完了ページに戻ってきたことですか、決済事業者からのサーバー間通知ですか?

🔴: リダイレクト(戻ってきたこと)を根拠に付与している

### Firebase / Supabase 等を使っている場合

> セキュリティルールの現物を見せてもらえますか? 特に、通貨やアイテムのデータに、クライアントから直接書き込める設定になっていないか確認したいです。

🔴: テストモードのまま / 通貨に書き込み権限がある

### ランキング・対戦がある場合

> スコアはクライアントが計算した結果を送っていますか? サーバー側で「ありえない値か」を検証していますか?

🔴: 送られた数値をそのまま保存している

> 対戦中、相手の非公開情報(手札・隠し配置など)は自分のクライアントに送られていませんか?

🔴: 表示しないだけで、データは届いている

### ログイン・アカウントがある場合

> パスワードはどういう形で保存していますか? 引き継ぎコードの桁数と、使い回しできるかどうかを教えてください。

🔴: パスワードが平文または復号可能な形 / 引き継ぎコードが短く推測可能

### UGC・チャットがある場合

> ユーザーが入力した文字列をそのまま画面に表示していますか? スクリプトが書かれても実行されない処理は入っていますか?

🔴: 対策なし(他人の画面で任意のコードが動く)

### リリース直前(全案件共通)

> 本番の公開ディレクトリに、.env・.gitディレクトリ・ソースマップが含まれていないことを確認してもらえますか? また、デバッグ機能とテストアカウントは本番ビルドから除外されていますか?

🔴: 含まれている / 「フラグで無効化している」(フラグはクライアント側で書き換えられる)

## 答えの読み方(赤信号になりやすい言い回し)

以下が返ってきたら、そこで納得せずもう一段掘る:

| 返答 | 何が問題か | 次に聞くこと |
|---|---|---|
| 「難読化しているので読めません」 | 難読化は解読を遅らせるだけ | 「読まれた場合でも成立しますか?」 |
| 「暗号化しているので大丈夫です」 | 鍵がクライアント内にあれば意味がない | 「復号の鍵はどこにありますか?」 |
| 「そのURLは公開していないので大丈夫です」 | URLを隠すのは対策ではない | 「URLを知っていても弾けますか?」 |
| 「普通はそんな操作しません」 | 攻撃者は普通の操作をしない | 「したらどうなりますか?」 |
| 「クライアントでチェックしています」 | クライアントのチェックは無効化できる | 「サーバー側でも同じ検証をしていますか?」 |
| 「今まで問題は起きていません」 | 気づいていないだけの可能性がある | 「起きていたら気づける仕組みはありますか?」 |
| 「対応済みです」 | 何をどう対応したかが不明 | 「どこで、どういう処理で防いでいますか?」 |

## 質問を送るときの文面テンプレート

**社内の別担当・外注に送る場合:**

> お疲れさまです。リリース前チェックとして、課金まわりの安全性について確認させてください。実装を疑っているわけではなく、**何かあったときに自分が説明できる状態にしておきたい**ためです。以下について、現状の作りを教えていただけますか。
>
> 1. (Q1)
> 2. (Q2)
> …
>
> お手すきのときで構いません。気になる点があれば、直し方も含めて一緒に考えます。

**公開済みのタイトルで、既に穴が疑われる場合(急ぎ):**

> お疲れさまです。急ぎで確認させてください。◯◯の挙動から、課金アイテムが不正に増やせる可能性を確認しています。まず被害の有無を知りたいので、
>
> 1. アイテムの増減ログは残っていますか(残っている場合、直近の異常な増加を確認できますか)
> 2. 該当機能だけを一時的に止めることは可能ですか、その場合どれくらいで反映されますか
>
> 犯人探しではなく、被害の把握と止血が目的です。手が空き次第、状況だけ共有してもらえると助かります。
