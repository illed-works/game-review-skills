# auth-and-api.md — 認証・認可・APIの守り

「自分が誰か(認証)」と「その人が何をしてよいか(認可)」は別物。ゲームの事故で多いのは**認可の抜け**で、ログインは正しくできているのに、他人のデータを触れてしまうパターン。

## 1. 他人のデータを触れる(認可漏れ / IDOR) — 🔴

最も見落とされやすく、最も被害が大きい。

**症状**: APIがユーザーIDを受け取り、そのIDのデータを返す・更新する。ログイン中のトークンとIDの一致を確認していない。

- プロフィール取得APIが、IDを指定すれば誰のものでも返す
- セーブデータ更新APIが、他人のIDを指定して上書きできる
- ギフト送信・フレンド申請が、送信元IDをクライアント指定にしている

**なぜ危険か**: IDが連番や推測可能なら、全ユーザーのデータが順に取得できる。個人情報漏洩事故になり、規模によっては報告義務が発生する。

**直し方**: **「誰のデータを操作するか」はリクエストのパラメータからではなく、認証トークンから決める。** クライアントがIDを送る必要がある場合も、サーバーがトークンの持ち主と照合し、不一致なら拒否する。この照合を、全エンドポイントで漏れなく行う(共通処理として入れるのが安全)。

**関連**: ユーザーIDが**連番・推測可能**なのは単体では🟡だが、上の照合が漏れていると被害が全数に及ぶので、組み合わせで🔴。

## 2. なりすまし・セッションの弱さ — 🔴〜🟡

- ユーザーIDだけでAPIを呼べる(トークンなし、またはIDがそのままトークン)
- トークンの署名検証をしていない・アルゴリズムの検証が甘い
- トークンに有効期限がない(一度漏れたら永久に使える)
- ゲストアカウントの引き継ぎコードが短い・推測可能・使い回せる
- パスワードを平文または可逆な形で保存している(🔴)

**ブラウザゲーム特有の注意**: 認証情報の保管場所は、httpOnly Cookie とlocalStorage で性質が異なる(前者はJSから読めないためスクリプト経由の盗難に強い一方、CSRF対策が別途要る)。**どちらでも構わないが、選んだ方に対応する対策がセットで入っているか**を確認する。

## 3. レート制限がない — 🟡(課金・抽選に絡むと🔴)

同じAPIを高速で叩き続けられる状態。

- ガチャ・抽選APIを連打され、想定外の負荷や在庫の不整合が起きる
- ログイン試行が無制限(総当たりでアカウントを乗っ取られる)
- ランキング投稿が無制限(ゴミデータで埋められる)
- 単純に、リクエスト量でサーバー費用が跳ね上がる

**直し方**: IPとアカウント単位のレート制限、ログイン失敗回数の制限、CDN・WAFの前段での制限。**特に、お金と在庫に触るAPIは必ず制限する。**

## 4. 通信・オリジンまわり — 🟡

- **HTTPSになっていない**(通信が読める・書き換えられる) → 🔴
- **CORSの許可が `*`(全許可)** かつ認証付きリクエストを受ける設定 → 他サイトからAPIを叩かれる
- WebSocketで、接続時に認証していない・部屋への参加権限を確認していない(**対戦ゲームで他人の部屋の情報が覗ける・介入できる**)
- 対戦の通信で、相手の手札・非公開情報がクライアントに送られている(**表示していなくても、届いていれば覗ける**。これは対戦ゲームで頻出の🔴)

## 5. 入力を信じている — 🟡〜🔴

サーバーがクライアントから受け取る値の検証。

- 文字数・型・範囲のチェックがない(異常に長い名前、負の数の個数、小数の個数)
- **負の数**が通ると、消費処理で残高が増えることがある(古典的な複製経路) → 🔴
- ユーザー名・チャットにスクリプトが書ける(表示時に実行される = XSS)。**UGCやチャットがあるなら必須確認項目**
- SQLを文字列連結で組み立てている(SQLインジェクション) → 🔴

## 6. 外部サービスの設定(BaaSを使っている場合) — 🔴になりやすい

Firebase / Supabase 等は、**初期設定やチュートリアル状態が「全開放」になっていることがある**。クライアントから直接DBを読み書きする構成では、ここが唯一の防御線になる。

確認すること:

- セキュリティルール(アクセス制御)が設定されているか。テストモードのまま公開していないか
- **通貨・アイテム・課金に関わるコレクションに、クライアントからの書き込み権限がないか**(あれば🔴。書き込みはサーバー側関数経由に限定する)
- 自分のデータだけ読み書きできる設定になっているか、他人の分まで読めないか
- 匿名認証を使っている場合、その匿名アカウントの権限範囲

**「ルールが書いてあること」と「ルールが正しいこと」は別。** 中身を読んで、通貨に書き込めないことを確認する。

#### ブラウザゲームで頻出の典型パターン: 「読み取りは堅いが、書き込みで通貨が素通し」

Firebase/Supabase 直結型(Cloud Functions を使わず、クライアントが直接DBを読み書きする構成)のブラウザゲームで**非常によく見る**穴。読み取り側は正しく「自分の分だけ」に制限されているのに、書き込み側のルールが「自分のドキュメントか」しか見ておらず、**ドキュメント内の通貨フィールドの改変を禁じていない**。この構成では、プレイヤーは自分のセーブデータの通貨(特に有償通貨)を任意の値に書き換えられる。

見分け方(コードが読める場合):
- クライアントバンドルに Cloud Functions 呼び出し(`httpsCallable` / `getFunctions` 等)が**無い**のに、DB書き込み(`setDoc`/`updateDoc`/`runTransaction`/`writeBatch`/`increment` 等)が**ある** → サーバー権威の付与処理が存在せず、クライアントが直接書いている強い兆候
- セーブデータが「クライアントのローカル保存(localStorage等)の辞書をそのままDBに同期している」形 → 通貨もその辞書の一部として素通しになりやすい
- 通信を見て、DBへの `Write` リクエストがクライアントから直接飛んでいる

**読み取りルールの非破壊確認**: 存在しない架空のユーザーID(実在の他人ではなくダミー)で、対象コレクションのドキュメントを1件だけ**読む**。permission-denied(403相当)が返れば「他人のデータは読めない」= 読み取りは堅い。これは誰のデータにも触れない、読み取りのみの安全なテスト。

**書き込みルールの非破壊確認**: 通貨フィールドを実際に改ざんすると自分のセーブを壊す副作用があるため、**値を変えない書き込み**で経路の開放だけを確かめる。具体的には、自分のドキュメントの無害なフィールド(更新時刻など)を**現在と同じ値**で書き戻す冪等な更新を1回送る。これが成功する(200相当)なら、「認証さえあれば自分のドキュメントに書き込める」= 同じ経路にある通貨フィールドも(サーバー側のフィールド単位検証が無い限り)書き換え可能、と判定できる。**通貨の値そのものは絶対に変えない** — 経路が開いていることの確認で判定には十分で、実改ざんはゲーム状態を壊す。

**直し方**: 通貨の増減をサーバー権威(Cloud Functions 等)に移し、クライアントからの直接書き込みでは通貨フィールドを**変更前と同じ値以外は拒否**するようルールで固定する。有償通貨は「サーバーでしか増やせない」状態をゴールにする。ルールを厳しくした結果、通貨以外の正当な更新(家具配置・スタミナ消費など)までブロックしていないかは必ず併せて確認する。

## 判定の目安

| 状況 | 重大度 |
|---|---|
| 他人のデータを読める・書ける | 🔴 |
| 通貨・アイテムのDBにクライアントから直接書き込める | 🔴 |
| HTTPSでない / パスワード平文 / SQL文字列連結 | 🔴 |
| トークンに期限がない、引き継ぎコードが弱い | 🟡(課金アカウントなら🔴) |
| レート制限なし | 🟡(ガチャ・課金・ログインは🔴) |
| CORS全許可(認証付きリクエストあり) | 🟡 |
| 対戦で非公開情報が相手クライアントに届いている | 🔴 |
