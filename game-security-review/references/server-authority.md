# server-authority.md — 課金・通貨・アイテムが増やせるか

このファイルが、このスキルの本丸。**ゲームの事故で最も損害が大きいのは、経済が壊れること。** 個人情報漏洩と違い、経済破壊は「静かに、じわじわ、気づかないうちに」進行し、気づいたときには市場に偽アイテムが溢れている。

## 判定の中心にある問い

> **その値は、誰が決めたのか。**

サーバーが自分で計算して決めた値なら信頼できる。クライアントが送ってきた値は、すべて自己申告であり、書き換えられている前提で扱わなければならない。この一点だけで、複製系の穴のほとんどは判定できる。

## 危険な設計パターン(見つけたら🔴)

### 1. クライアントが「結果」を送ってくる

- クライアントが「クリアした。報酬は◯◯を3個」と送り、サーバーがそのまま付与する
- クライアントが「スコア12000」と送り、サーバーがそのまま保存する
- クライアントが「レベルアップした。新レベルは50」と送る
- クライアントが「所持金は10000になった」と送り、サーバーが上書きする

**なぜ危険か**: 送られてくる数字は書き換えられる。上限チェックすら、上限内の値を送られたら意味がない。

**直し方**: サーバーが「入力(プレイヤーの操作・消費したもの)」だけを受け取り、**結果はサーバー側で計算する**。リアルタイム性が高くてサーバー計算が難しい場合でも、最低限「その値が物理的にありえるか」の検証(所要時間・上限・前回値との差分)をサーバーで行う。

### 2. 価格・コストをクライアントから受け取る

- 購入APIが「アイテムID」と一緒に「価格」を受け取っている
- 消費するアイテムの個数をクライアントが指定し、サーバーが検算していない
- 割引率・セール価格をクライアントが送っている

**直し方**: 価格・コストは**サーバー側のマスタデータだけを正とする**。クライアントから来た価格は表示確認用として無視するか、一致しなければエラーにする。

### 3. 同じリクエストが二度効く(二重付与・複製の直接原因)

- ネットワークが切れたときのリトライで、同じ購入・同じ報酬受け取りが2回処理される
- 同時に複数のリクエストを送ると、残高チェックをすり抜けて両方成功する(在庫・通貨の同時消費)

**なぜ危険か**: これが「課金アイテムの複製」の最も一般的な原因。攻撃者は特別な技術を必要とせず、同じ操作を繰り返すだけでよい。

**直し方**:
- 付与・消費のリクエストに**一意なID(冪等キー)**を持たせ、サーバー側で「このIDはもう処理済み」を記録して二度目は無視する
- 残高の増減は**データベースのトランザクション**でまとめ、同時実行でも整合するようにする(「読んでから書く」の間に割り込まれない作りにする)
- 「受け取り済みフラグ」は、付与処理と**同じトランザクションの中で**立てる。別処理にすると隙間ができる

### 4. 課金レシートの検証が甘い

- ストア(App Store / Google Play / Steam)のレシートをサーバーで検証していない、クライアント側で検証している
- 同じレシートを再送すると、何度でも付与される(レシートの使い回し)
- Web決済で、決済完了ページに戻ってきたこと(リダイレクト)を根拠に付与している

**直し方**: レシート検証は**必ずサーバーからストアの検証APIに問い合わせる**。検証済みレシートのトランザクションIDを保存し、**同じIDは二度と受け付けない**。Web決済は、リダイレクトではなく**決済事業者からのサーバー間通知(Webhook)**を根拠に付与し、通知の署名を検証する。

### 5. セーブデータをクライアントが持っている

- 進行状況・所持アイテムをlocalStorage / IndexedDB / Cookie / ローカルファイルに保存し、それをそのまま信じている
- クライアントのセーブデータをサーバーに丸ごとアップロードして保存している(クラウドセーブ)

**判定**: 課金要素がなく、ランキングも対戦もない完全なシングルプレイなら、これは**🟡以下**でよい(壊れて困るのは本人だけ)。ただし**ランキング・対戦・課金がある時点で🔴**。「セーブデータの暗号化」「チェックサム」は、クライアント内に鍵があるので破られる。時間稼ぎ以上の意味はないと理解した上で使う。

### 6. 無料通貨・広告リワードの水増し

- 広告視聴の完了をクライアントの申告で判定している
- ログインボーナス・デイリー報酬の判定にクライアントの時刻を使っている(端末の時計を進めるだけで何度でも受け取れる)

**直し方**: 広告リワードは広告SDKの**サーバー間コールバック(S2S callback)**で検証する。日付の判定は**必ずサーバー時刻**で行う。

## サーバーがない構成の場合

「サーバーなし・クライアント完結」の場合、上の対策はどれも成立しない。この場合の判定はシンプル:

- **課金・ランキング・対戦があるなら、サーバーなしは成立しない。** 設計をやり直す必要がある(🔴)
- **完全にオフラインのシングルプレイなら、改ざんは基本的に許容してよい。** ただし「実績・ランキングを後から足す予定がある」なら、その時点で作り直しになることを明示しておく

## 確認するときの見どころ(コードが読める場合)

サーバー側のAPI実装で、以下の観点を見る:

- 付与・消費のエンドポイントが受け取っているパラメータ一覧 — **数量・価格・報酬内容が含まれていないか**
- 付与処理の中に、冪等キーの重複チェックまたは「受け取り済み」判定があるか
- 残高の更新がトランザクション内か、単純な読み書きか
- レシート検証が外部APIへの問い合わせを実際に行っているか(スタブや常にtrueを返す実装になっていないか)
- 検証結果を無視して先へ進む分岐(エラーを握りつぶして付与している)がないか

クライアント側しか見られない場合は、**通信で何を送っているか**から逆算する。送信内容に「報酬」「価格」「スコア」「所持数」が含まれていれば、サーバーがそれを信じている可能性が高い。ただし**サーバーが検算している可能性も残る**ので、断定せず「送信内容から見て要確認、サーバー側の実装確認が必要」として質問リストに送る。
