# client-exposure.md — クライアントに出てはいけないもの

前提: **ブラウザに配信された時点で、そのファイルは全世界に公開されている。** 開発者ツールを開けばJSもアセットも通信も見える。難読化・minifyは読みにくくするだけで、隠す機能ではない。「隠したつもり」が最も事故を生む。

## 1. 秘密情報(見つけたら🔴、即座に無効化が必要)

クライアント側のコード・設定ファイル・アセットに以下があってはいけない。

| 種類 | 具体例 | 漏れると何が起きるか |
|---|---|---|
| サーバー側APIキー・シークレット | 決済事業者の秘密鍵、外部APIのsecret key、署名用の鍵 | 課金の偽装、他人名義の請求、なりすまし |
| クラウドの認証情報 | AWSのアクセスキー、GCPのサービスアカウントJSON | インフラ全体の乗っ取り、データ全消し、高額請求 |
| データベース接続情報 | 接続文字列、DBのユーザー名・パスワード | 全プレイヤーデータの閲覧・改ざん |
| 管理者用の情報 | 管理画面のURL、管理者用トークン、社内ツールのエンドポイント | アイテム付与・BAN操作の乗っ取り |
| 通知・監視系のトークン | Slack Webhook URL、Sentry等のDSN(書き込み権限つき) | 社内へのなりすまし投稿、ログ汚染 |
| 内部向けのエンドポイント | デバッグAPI、社内ネットワーク前提のURL | 想定外の経路からの操作 |

### 注意: 「公開してよい鍵」と混同しない

一部のサービスは**クライアントに置く前提の公開鍵**を配布している(Firebaseの`apiKey`、Stripeのpublishable key、各種SDKのクライアントID等)。これらは露出していても即座に事故ではない。**危険なのは、その鍵の権限設定が緩い場合**。

- Firebaseの`apiKey`自体は公開前提。**問題はセキュリティルールが「誰でも読み書き可」になっていること** → その場合は🔴
- Stripeのpk_は公開前提、sk_は🔴
- 「公開前提の鍵だから安全」で終わらせず、**権限設定側を必ず確認する**

判定に迷ったら、その鍵の提供元の公式ドキュメントで「クライアントに置いてよいか」を確認する(記憶で断定しない)。

### 探し方(文字列検索のパターン)

ソースやビルド成果物を全文検索する。大文字小文字は無視して探す:

```
secret / private_key / apikey / api_key / access_key / token
password / passwd / credential / auth
sk_live / sk_test / AKIA / -----BEGIN
admin / debug / internal / staging / localhost
.amazonaws.com / hooks.slack.com
```

加えて、**長いランダム文字列(20文字以上の英数字が連続するリテラル)**を目視で確認する。

**発見した値そのものをレポートや検索クエリに書かない。** 「◯◯ファイルの◯行目にAWSのアクセスキーらしき文字列(先頭`AKIA...`)」の形で伏せる。

### 見つかったときに伝えること

キーが漏れていた場合、**削除するだけでは不十分**。すでに配信済みなら、誰かが控えている前提で対応する:

1. その鍵を**無効化(revoke)して新しい鍵を発行する**
2. 新しい鍵は**クライアントに置かない設計に変える**(サーバー経由で呼ぶ)
3. 利用ログを確認し、不正利用の痕跡を調べる
4. リポジトリの**過去のコミット履歴からも消す**(履歴に残っていれば漏洩は継続する。`infra-and-release.md`参照)

## 2. デバッグ機能・チート機能の残骸(🔴〜🟡)

- デバッグメニュー、通貨追加ボタン、ステージスキップが本番ビルドに残っている
- URLパラメータやコンソールコマンドで開発者モードに入れる(`?debug=1`等)
- テスト用アカウント・マスターパスワードがコードに書かれている
- 開発時に使っていた「サーバー検証をスキップするフラグ」が残っている

**判定**: デバッグ機能から通貨・アイテムが増やせるなら🔴。表示だけの機能なら🟡。**ビルド設定でフラグを切っているだけ(コードは含まれている)場合、フラグはクライアント側で書き換えられる**ので、通貨に触れる機能は「ビルドから物理的に除外する」必要がある。

## 3. 未公開コンテンツ・ネタバレの露出(🟡、ものによっては事業影響大)

- 未実装・未発表のキャラ、ステージ、イベントのアセットが同梱されている
- マスタデータに未公開アイテムの名前・性能・実装予定が含まれている
- コラボ相手の名前やロゴが先に入っている(**IP案件では契約違反になりうるので、この場合は🔴扱いでlegal-reviewにも回す**)

ゲームの「データマイニング」は日常的に行われ、SNSで即座に拡散する。**未公開情報は、実装のタイミングまでクライアントに配信しない**(サーバー配信・後日DLに分ける)のが対策。

## 4. マスタデータ・ゲームバランス情報の露出(多くは🟢〜🟡)

ドロップ率、内部パラメータ、乱数テーブルなどが読める状態は、**基本的に避けられない**。ここを「隠せている」と誤認しないことが大事で、以下の観点で見る:

- 読まれても**経済が壊れないか**(壊れるなら`server-authority.md`の問題)
- 確率表示が必要な要素(ガチャ等)で、**表示している確率と実データが食い違っていないか** → 食い違いは景表法リスクなのでgame-legal-reviewにも回す(🔴)
- 乱数のシードや抽選をクライアントで行っていないか(結果を引き直せる) → 抽選は**サーバーで行う**

## 5. 個人情報・他人のデータがクライアントに落ちてくる(🔴)

- ランキングAPIのレスポンスに、表示に不要な情報(メールアドレス、端末ID、生年月日、課金額)が含まれている
- フレンド一覧のAPIが、他人の内部IDやアクセストークンまで返している
- エラーメッセージにサーバーの内部情報(SQL文、ファイルパス、スタックトレース)が出る

**画面に表示していなくても、通信で送られていれば漏洩している。** APIのレスポンスは「表示に必要な項目だけを返す」設計にする。この項目は個人情報保護法・GDPRにも直結するので、該当したらgame-legal-reviewにも回す。
