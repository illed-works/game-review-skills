# platform-notes.md — プラットフォーム別の勘所

大原則(クライアントは信用しない)はどこでも同じ。ここでは**プラットフォームごとに特に事故が起きる箇所**を挙げる。該当するものだけ読めばよい。

## ブラウザ(素のJS / Phaser / Pixi / Cocos など)

最も中身が見えるプラットフォーム。開発者ツールで、コード・通信・保存データがすべて閲覧・編集できる。

- **JSの変数・関数は実行中に書き換えられる。** 「所持金の変数を書き換える」程度は誰でもできる。だから所持金の正はサーバーになければならない
- **通信は開発者ツールのネットワークタブで全部見える。** 送信内容に報酬・価格・スコアが載っていないか確認する
- localStorage / IndexedDB / Cookie は自由に編集できる
- 難読化(minify・obfuscate)は解読を遅らせるだけ。**難読化を根拠に「読まれない」と判定しない**
- ソースマップを本番に出していないか(`infra-and-release.md`参照)
- 広告・解析タグを入れる場合、そのスクリプトはゲームと同じ権限で動く。信頼できる提供元か、必要な範囲か

**社内での典型的な事故**: ブラウザゲームは「手軽だから」とサーバーを最小構成にしがちで、その結果クライアント権威のまま課金を載せてしまう。**課金を載せる判断をした時点で、サーバー設計を1回見直す**のが正しい順序。

**Firebase/Supabase 直結型は特に注意**: ブラウザゲームで最も多いバックエンド構成が、これらBaaSにクライアントから直接つなぐ形。手軽な反面、サーバー権威の付与処理(Cloud Functions等)を挟まずに通貨をクライアントが直接DBに書く作りになりやすい。この構成に出会ったら、防御の最後の砦は**DBのセキュリティルール一点**になるので、ルールの読み取り側と書き込み側を分けて確認する。特に「読み取りは自分の分だけに守られているのに、書き込み側で通貨フィールドが素通し」という組み合わせが頻出。判定と非破壊の確認手順は `auth-and-api.md` の「ブラウザゲームで頻出の典型パターン」を参照。AIコーディングで生成されたゲームは、この構成のまま出ていることが多い。

## Unity / Godot などのWebGL書き出し

「コンパイルされているから読めない」と誤解されやすいが、**wasmもアセットバンドルも解析ツールが普及している**。

- Unity WebGLのビルド成果物からは、アセットもコード構造も抽出できる
- IL2CPPでも文字列リテラル(APIキー等)は取り出せる。**「ビルドすれば隠せる」は成立しない**
- アセットバンドルの暗号化は時間稼ぎ。鍵はクライアント内にある
- PlayerPrefs / ローカルセーブは平文で編集可能

判定はブラウザJSと同じ基準でよい。**「ネイティブに近いから安全」という格上げをしない。**

## モバイル(iOS / Android)

- **課金レシートの検証は必ずサーバーで**(`server-authority.md`参照)。クライアント検証は無効
- Androidのapkは容易に取り出せ、逆コンパイル・改造版apkが出回る。改造版の配布そのものは止められないので、**サーバー側で「その申告を信じない」ことが唯一の防御**
- 通信の中身を見るツール(プロキシ)も一般的。証明書ピンニングは有効な追加防御だが、これも突破可能な時間稼ぎ
- 端末の時計は自由に変えられる。**日付判定は必ずサーバー時刻**
- root/脱獄検知やエミュレータ検知は「あれば良い」レベル。これに依存した設計にしない

## Steam

- 実行ファイルは手元にあるので、メモリ改変ツールでの数値書き換えは日常的に行われる。**シングルプレイのみなら大半は許容範囲**
- ただし**実績・ランキング・統計(Steamworks Stats)はクライアントから送られる**ので、改ざんされる前提で扱う。ランキングに賞金や換金性を絡めるなら、サーバー側の別検証が必要(絡めるならgame-legal-reviewにも回す)
- マルチプレイでホストがプレイヤーの場合(P2P)、**ホストが有利になる改ざんができる**。競技性が高いならホストをサーバー側に置く
- ワークショップ・MOD対応は、**ユーザー製コンテンツが他人の環境で動く**ということ。スクリプト実行を伴うMODを許すなら、その前提でリスクを説明する

## Roblox

Robloxは**サーバー/クライアントの境界が仕組みとして明確**な反面、境界の扱いを間違えると即座に穴になる。

- **LocalScript(クライアント側)は完全に信用できない。** エクスプロイトツールが広く出回っており、クライアント側の判定はすべて書き換えられる前提
- **RemoteEvent / RemoteFunction は、誰でも任意の引数で呼べる。** 「UIからしか呼ばれないはず」は成立しない。サーバー側のハンドラで、**呼び出し元の権限・引数の型・値の範囲・呼び出し頻度**を必ず検証する
- 特に危険: RemoteEventの引数で「付与するアイテム」「増やす通貨量」を受け取っている設計 → 🔴。サーバー側が自分で決める形に直す
- Robuxの購入処理・データストアの更新はサーバー側でのみ行う
- DataStoreの更新は失敗しうる。リトライで二重付与にならないか確認する
- **未成年ユーザーが多いプラットフォームなので、チャット・UGCの安全性はレーティングと運営責任に直結する。** 該当したらgame-legal-reviewにも回す

## 共通: プラットフォームを問わず必ず確認すること

どのプラットフォームでも、この3つは必ず見る。

1. 通貨・アイテムの増減を**最終的に決めているのは誰か**(サーバーでなければ🔴)
2. クライアント内に**サーバー側の鍵**がないか
3. 同じリクエストを二度送ったときに**二度効かないか**
