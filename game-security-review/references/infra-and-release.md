# infra-and-release.md — 配信とリポジトリの事故

コードは正しくても、**置き場所と配り方**で漏れる。ここは実装の巧拙と関係なく起きるので、リリース前に必ず1回チェックする。ブラウザゲームの事故はここ由来が非常に多い。

## 1. 公開ディレクトリに置いてはいけないもの

Webサーバーの公開領域に混ざっていると、URLを叩くだけで誰でも取得できる。

| ファイル | 中身 | 重大度 |
|---|---|---|
| `.env` / `.env.production` | APIキー・DB接続情報の塊 | 🔴 |
| `.git/` ディレクトリ | **ソースコード全部と全履歴が復元できる** | 🔴 |
| `*.map`(ソースマップ) | 難読化前の元ソース(コメント込み)が復元できる | 🟡(鍵が含まれれば🔴) |
| `config.json` / `settings.yml` 等 | 環境設定、内部URL | 🟡〜🔴 |
| バックアップファイル(`.bak` `.old` `~`) | 旧版のソース | 🟡 |
| `node_modules/` `src/` `docs/` | 開発物一式 | 🟡 |
| DBダンプ・CSV・Excel | 実データ | 🔴 |

**確認方法**: 公開URLの直下にこれらのパスが存在するかを確認する(閲覧のみ。ツールによる総当たり探索はしない)。デプロイの仕組み側で「公開するファイルを列挙する」方式(必要なものだけコピー)にすると、この種の事故は構造的に防げる。除外リスト方式は、書き忘れると漏れる。

**ディレクトリ一覧表示(ディレクトリリスティング)が有効になっていないか**も確認する。有効だと、ファイル名が全部見える。

## 2. リポジトリの履歴に残った秘密情報 — 🔴

**「コミットして、後から消した」は消えていない。** 履歴から復元できるので、公開リポジトリなら漏洩は継続している。

確認:

- リポジトリが公開設定になっていないか(GitHub/GitLabのpublic)
- 過去に鍵・`.env`・認証情報をコミットしていないか
- `.gitignore` に `.env` や認証情報が入っているか(入っていなければ、これから事故る)

**見つかった場合の対応**: 履歴の書き換えより先に、**その鍵を無効化して再発行する**。履歴を消しても、既に誰かがクローンしていれば手遅れなので、「鍵を無効にする」以外に有効な対策はない。

## 3. 管理画面・内部ツールの露出 — 🔴

- 運営用の管理画面が、ゲームと同じドメイン・推測可能なパス(`/admin`)にある
- 管理画面にIP制限も多要素認証もない
- 「URLを知らないから安全」で運用している(URLはリファラやログや履歴から漏れる)
- 開発・ステージング環境が、本番と同じデータで、認証なしで公開されている(**これは非常に多い。検索エンジンに載ることもある**)

**直し方**: 管理系は別ドメイン・IP制限・多要素認証。ステージング環境はBasic認証か社内ネットワーク限定にし、`noindex`を付ける。**本番データをステージングにコピーするなら、個人情報はマスクする。**

## 4. クラウドストレージの公開設定 — 🔴

アセット配信でS3・GCS・R2等を使う場合:

- バケットが**全体公開かつ一覧可能**になっていないか(中身のファイル名が全部見える → 未公開アセットが読める)
- 書き込み権限が公開になっていないか(**アセットを差し替えられる = ゲーム内に任意の画像・スクリプトを配信される**)
- 署名付きURLの有効期限が長すぎないか

**「読み取り公開」は配信目的なら正しいが、「一覧公開」と「書き込み公開」は別物**として分けて確認する。

## 5. 依存ライブラリ — 🟡

- 使っているライブラリに既知の脆弱性がないか(`npm audit`等の結果を確認してもらう)
- 出所の怪しいライブラリ、更新が止まって久しいライブラリを使っていないか
- CDNから外部スクリプトを読み込んでいる場合、**その配信元が乗っ取られたら任意のコードが実行される**。整合性チェック(SRI)を付けているか

依存の脆弱性は、**ゲームに実際に効くものかどうか**で重大度を分ける。開発ツールにしか使わないパッケージの警告で🔴を出さない。

## 6. リリース作業そのもの — 🟡

- 誰が本番にデプロイできるかが管理されているか
- デプロイ後に**元に戻せるか**(ロールバック手順があるか)
- 本番の設定変更が記録に残るか

事故が起きたときに「すぐ戻せる」ことは、被害を最小化する最大の武器。**この項目は`ops-and-incident.md`と合わせて確認する。**

## リリース前の最終ゲート(公開ボタンを押す前に)

このリストは、公開直前に毎回確認する。仕様や実装が変わっていなくても、配信のたびに起こりうる事故だから。

1. 公開領域に `.env` / `.git` / ソースマップ / バックアップが混ざっていないか
2. デバッグ機能・テストアカウントが本番ビルドから除外されているか
3. クライアント内に、サーバー側の鍵・管理URLが含まれていないか
4. ステージング環境が公開状態のまま放置されていないか
5. ストレージのバケットが書き込み公開になっていないか
6. 通貨・アイテムのDBに、クライアントから直接書き込めないか
7. 何かあったときに**止められる手段**があるか(緊急停止・ロールバック)
